\section{Introducción}
% ================================================================

El \textit{BombLab} es un ejercicio clásico de ingeniería inversa. El binario solicita seis claves al usuario. Si alguna es incorrecta, la ``bomba explota'' y el proceso termina con error. En la versión tradicional las claves están codificadas en el binario y pueden encontrarse mediante análisis estático del código ensamblador.

La variante presentada en este trabajo introduce una diferencia fundamental: \textbf{las claves no están almacenadas en el ejecutable sino que se generan aleatoriamente en cada ejecución}. Esto hace que el análisis estático sea insuficiente: no existe ninguna clave fija que pueda extraerse del binario con antelación.

El objetivo del trabajo es escribir un programa en C que:
\begin{enumerate}[label=\arabic*.]
    \item Ejecute el binario \texttt{Bomba} como proceso hijo.
    \item Utilice \texttt{ptrace} para interceptar su ejecución en tiempo real.
    \item Lea el valor esperado en cada fase directamente desde los registros o la memoria del proceso.
    \item Inyecte ese valor en el operando que representa la respuesta del usuario, justo antes de que se evalúe la comparación.
    \item Logre pasar las seis fases sin que la bomba detone.
\end{enumerate}

Este informe detalla los conceptos teóricos involucrados, el análisis del ejecutable mediante ingeniería inversa y el diseño del programa \texttt{desactivador.c}.

\section{Análisis del ejecutable}
% ================================================================

\subsection{Herramientas y metodología}

El análisis del binario se realizó en dos etapas:

\begin{enumerate}[label=\arabic*.]
    \item \textbf{Exploración con editor hexadecimal:} Se utilizó la herramienta web \texttt{hexed.it} para inspeccionar el contenido del binario. Esto permitió identificar el tipo de dato de la clave de cada fase.
    
    \includegraphics[width=0.55\textwidth]{hex.png}

    \item \textbf{Desensamblado con \texttt{objdump}:}

\begin{lstlisting}[style=termstyle]
objdump -d -M intel Bomba > desensamblado.txt
\end{lstlisting}

    El análisis sobre el código desensamblado consistió en:
    \begin{itemize}
        \item Localizar las instrucciones de comparación (\texttt{cmp}, \texttt{ucomiss}, \texttt{call strcmp}) de cada fase.
        \item Rastrear \textbf{hacia atrás} desde cada comparación para encontrar en qué registro o posición del stack quedaba almacenada la clave generada aleatoriamente o, en otros casos, si se sabe en qué registro está lo ingresado por el usuario, alcanza con analizar las instrucciones de comparación.
        \item Rastrear la llamada a \texttt{sscanf} anterior para identificar, mediante la convención de llamada, en qué dirección de memoria quedaba el input del usuario.
    \end{itemize}
\end{enumerate}

\subsection{Información general}

\begin{lstlisting}[style=termstyle]
$ file Bomba
Bomba: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV),
       dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
       BuildID[sha1]=2ec7e50a..., for GNU/Linux 3.2.0, stripped
\end{lstlisting}

Características relevantes:
\begin{itemize}
    \item \textbf{Arquitectura}: x86-64 (64 bits, little-endian).
    \item \textbf{Tipo}: ELF PIE, enlazado dinámicamente.
\end{itemize}

\subsection{Convención de llamada en x86-64}

En la arquitectura x86-64, los primeros seis argumentos de una función se pasan en los registros: \texttt{rdi}, \texttt{rsi}, \texttt{rdx}, \texttt{rcx}, \texttt{r8}, \texttt{r9}. El valor de retorno queda en \texttt{rax}.

Conocer esta convención es esencial para el análisis del desensamblado. En particular, para las dos funciones que procesan el input del usuario:

\begin{itemize}
    \item \textbf{\texttt{fgets(buffer, tamaño\_buffer, archivo\_entrada)}}: \texttt{rdi} = buffer donde queda el input del usuario; \texttt{rsi} = tamaño máximo en bytes; \texttt{rdx} = archivo de entrada (\texttt{stdin}).
    \item \textbf{\texttt{sscanf(str\_a\_convertir, formato, \&destino)}}: el valor convertido queda en la dirección apuntada por \texttt{rdx}. Observando el valor de \texttt{rdx} antes de la llamada se sabe exactamente en qué posición del stack deposita \texttt{sscanf} la respuesta del usuario.
\end{itemize}

\subsection{Flujo de ejecución}

Al iniciarse, la función \texttt{main} del binario sigue este patrón:
\begin{enumerate}[label=\arabic*.]
    \item Se generan claves al azar.
    \item Se guardan en registros especificos.
    \item Para cada fase: imprime un mensaje solicitando un ingreso, lee la respuesta del usuario con \texttt{fgets} + \texttt{sscanf} (o \texttt{fgets} + \texttt{strcmp} para la fase de texto), compara con la clave esperada y, si no coincide, llama a la función que imprime el mensaje de explosión y termina.
\end{enumerate}

\subsection{Las seis fases}

El análisis del desensamblado permitió identificar las instrucciones de comparación de cada fase y los registros involucrados:

\begin{center}
\begin{tabular}{cclll}
\toprule
\textbf{Fase} & \textbf{Tipo} & \textbf{Offset ELF} & \textbf{Instrucción de comparación} & \textbf{Clave en} \\
\midrule
1 & Entero & \texttt{0x176e} & \texttt{cmp [rsp+0x44], r15d}         & registro \texttt{r15d} \\

3 & Entero & \texttt{0x182f} & \texttt{cmp [rsp+0x44], ebx}          & registro \texttt{ebx} \\
4 & Texto  & \texttt{0x18ae} & \texttt{call strcmp(rdi, rsi)}         & \texttt{rsi} $\to$ string en \texttt{[rsp+0x50]} \\

\subsection{Análisis detallado por fase}

\subsubsection*{Fases 1, 3 y 5 — Enteros}

Para la Fase~1, la instrucción de comparación es:

\begin{lstlisting}[style=asmstyle, caption={Comparacion de entero --- Fase 1 (offset 0x176e)}]
176e:  44 39 7c 24 44   cmp  DWORD PTR [rsp+0x44], r15d
1773:  0f 85 22 02 00   jne  199b    ; BOOM! si no coincide
\end{lstlisting}

Para saber por qué la clave está en \texttt{r15d}, se rastreó hacia atrás en el desensamblado:

\begin{lstlisting}[style=asmstyle, caption={Cadena de generacion de clave --- Fase 1}]
11f0:  e8 9b ff ff ff   call  rand
11f5:  41 89 c7         mov   r15d, eax
...
1747:  4c 8d 74 24 44   lea   r14, [rsp+0x44]
174c:  e8 df f9 ff ff   call  fgets
...
1753:  4c 89 f2         mov   rdx, r14
1760:  e8 fb f9 ff ff   call  sscanf
\end{lstlisting}

Se observa que \texttt{rand()} devuelve un entero aleatorio en \texttt{eax}, que se copia inmediatamente a \texttt{r15d}. Por otro lado, antes de llamar a \texttt{fgets} se carga en \texttt{r14} la dirección efectiva de \texttt{[rsp+0x44]}. Luego, al llamar a \texttt{sscanf}, ese mismo valor se pasa como tercer argumento en \texttt{rdx} — que, según la convención de llamada, es el destino del valor convertido. Por lo tanto, \texttt{[rsp+0x44]} contiene la respuesta del usuario y debe sobreescribirse con el valor de \texttt{r15d}.

Las Fases~3 y~5 siguen la misma estructura, con la diferencia de que la clave queda en \texttt{ebx}. Dado que el registro \texttt{r14} no se modifica entre fases, el input del usuario sigue llegando a \texttt{[rsp+0x44]}.

\begin{lstlisting}[style=asmstyle, caption={Fase 3 (offset 0x182f) y Fase 5 (offset 0x1911)}]
; Fase 3
182f:	39 5c 24 44          	cmp    DWORD PTR [rsp+0x44],ebx
1833:	0f 85 62 01 00 00    	jne    199b
...
; Fase 5
1911:	39 5c 24 44          	cmp    DWORD PTR [rsp+0x44],ebx
1915:	0f 85 80 00 00 00    	jne    199b
\end{lstlisting}

Volviendo a la comparación, si vamos a \texttt{199b}, nos encontramos:
\begin{lstlisting}[style=asmstyle, caption={Código en \texttt{199b}}]
199b:	31 c0                   xor    eax,eax
199d:	e8 fe 00 00 00       	call   1aa0
\end{lstlisting}
Es decir, se limpia el contenido del registro \texttt{eax} y realiza una \texttt{call} a \texttt{1aa0}. Yendo a 1aa0, encontramos:
\begin{lstlisting}[style=asmstyle, caption={Código en \texttt{1aa0}}]
1aa0:	f3 0f 1e fa           	endbr64
1aa4:	50                      push   rax
1aa5:	58                      pop    rax
1aa6:	48 8d 3d 5b 05 00 00 	lea    rdi,[rip+0x55b]
1aad:	48 83 ec 08          	sub    rsp,0x8
1ab1:	e8 3a f6 ff ff       	call   puts
1ab6:	bf 01 00 00 00       	mov    edi,0x1
1abb:	e8 c0 f6 ff ff          call   exit
\end{lstlisting}
Es importante notar que carga en el \texttt{RDI} una dirección de memoria, hace un llamado a la función \texttt{puts} y llama a una función \texttt{exit}. Dicho de otro modo, se puede deducir que imprime el mensaje explosión de bomba y termina el programa.
\subsubsection*{Fases 2 y 6 — Punto flotante}

En la Fase~2, la comparación se realiza con la instrucción \texttt{ucomiss} (\textit{Unordered Compare Scalar Single-Precision}):

\begin{lstlisting}[style=asmstyle, caption={Comparacion de float --- Fase 2 (offset 0x17c2)}]
17c2:  f3 0f 10 5c 24 1c   movss   xmm3, [rsp+0x1c]
17c8:  0f 2e 5c 24 48      ucomiss xmm3, [rsp+0x48]
17cd:  0f 8a c8 01 00 00   jp      199b
17d3:  0f 85 c2 01 00 00   jne     199b
\end{lstlisting}

La instrucción \texttt{ucomiss} compara dos valores en precisión simple (\texttt{float} de 32 bits). Activa el \textit{parity flag} (indicador de paridad: bit del registro de flags que se activa cuando algún operando es un valor NaN) si alguno de los operandos no es un número válido. Las dos ramas condicionales (\texttt{jp} y \texttt{jne}) garantizan que tanto NaN como valores distintos detonen la bomba.

La generación del float se rastreó hacia atrás:

\begin{lstlisting}[style=asmstyle, caption={Cadena de generacion del float --- Fase 2}]
11f8:  e8 93 ff ff ff      call  rand
11fd:  66 0f ef c0         pxor  xmm0, xmm0
1201:  f3 0f 2a c0         cvtsi2ss xmm0, eax
1205:  f3 0f 5e 05 f7 0d   divss xmm0, [rip+0xdf7]
120d:  f3 0f 11 44 24 1c   movss [rsp+0x1c], xmm0
\end{lstlisting}

Primero, \texttt{rand()} genera un entero en \texttt{eax}. Luego, \texttt{pxor xmm0, xmm0} inicializa el registro en cero. La instrucción \texttt{cvtsi2ss} (\textit{Convert Scalar Integer to Scalar Single}) convierte el entero de \texttt{eax} a un \texttt{float} de 32 bits en \texttt{xmm0}. A continuación, \texttt{divss} (\textit{Divide Scalar Single-precision}) lo divide por una constante almacenada en el segmento de datos del binario. El resultado se guarda en \texttt{[rsp+0x1c]} con \texttt{movss} (\textit{Move Scalar Single Precision}). El input del usuario, procesado por \texttt{sscanf} con formato \texttt{\%f}, se deposita en \texttt{[rsp+0x48]}.

La Fase~6 sigue el mismo patrón con el registro \texttt{xmm4} y los offsets \texttt{[rsp+0x3c]} (clave) y \texttt{[rsp+0x4c]} (input del usuario).

\begin{lstlisting}[style=asmstyle, caption={Comparacion de float --- Fase 6 (offset 0x195f)}]
1959:	f3 0f 10 64 24 3c    	movss   xmm4,DWORD PTR [rsp+0x3c]
195f:	0f 2e 64 24 4c       	ucomiss xmm4,DWORD PTR [rsp+0x4c]
1964:	7a 35                	jp      199b
1966:	75 33                	jne     199b
\end{lstlisting}
\subsubsection*{Fase 4 — Texto}

La Fase~4 pide al usuario que ingrese un string. La comparación se hace con \texttt{strcmp}:
\begin{lstlisting}[style=asmstyle, caption={Ingreso del usurio, eliminacion del newline y comparacion de string --- Fase 4}]
187e:	48 8b 15 8b 27 00 00 mov  rdx,QWORD PTR [rip+0x278b]        # 4010 <stdin@GLIBC_2.2.5>
1885:	be 64 00 00 00       mov  esi,0x64
188a:	48 89 ef             mov  rdi,rbp
188d:	e8 9e f8 ff ff       call fgets
1892:  48 8d 35 8e 07 00 00  lea  rsi, [rip+0x78e]
1899:  48 89 ef              mov  rdi, rbp
189c:  e8 6f f8 ff ff        call strcspn
18a1:  48 8d 74 24 50        lea  rsi, [rsp+0x50]
18a6:  48 89 ef              mov  rdi, rbp
18a9:  c6 44 04 60 00        mov  BYTE [rsp+rax+0x60], 0x0
18ae:  e8 8d f8 ff ff        call strcmp
18b3:  85 c0                 test eax, eax
18b5:  0f 85 e0 00 00 00     jne  199b
\end{lstlisting}
Se empieza pidiéndole al usuario una cadena con la función \texttt{fgets}. Considerar que el \texttt{rdi} apunta al buffer (donde va a quedar el dato), en \texttt{esi} va el tamaño del buffer (\texttt{0x64} en base 16, lo cual es 100 en base 10) y en \texttt{rdx} se carga un puntero a la entrada estándar. Antes de llamar a \texttt{strcmp}, la bomba elimina el carácter de nueva línea que \texttt{fgets} deja al final del buffer. Para esto usa \texttt{strcspn(s1, s2)}, que devuelve en \texttt{rax} el índice de la primera ocurrencia de cualquier carácter de \texttt{s2} en \texttt{s1}. En este caso, busca el carácter \texttt{'\textbackslash n'} en el buffer del usuario y coloca un \texttt{0} en esa posición para terminarlo.

En el momento de \texttt{call strcmp}: \texttt{rdi} apunta al buffer del usuario y \texttt{rsi} apunta al string esperado en \texttt{[rsp+0x50]}. La instrucción \texttt{test eax, eax} activa el \textit{zero flag} si \texttt{eax} es cero, es decir, si las cadenas son iguales.

\section{Conceptos fundamentales}
% ================================================================

\subsection{Formato ELF y ejecutables PIE}

Los programas en Linux se almacenan en formato \textbf{ELF} (\textit{Executable and Linkable Format}). Un archivo ELF contiene uno o más \textbf{segmentos de carga} (\textit{load segments}): regiones del archivo que el sistema operativo copia directamente en la memoria virtual del proceso al ejecutarlo. Los segmentos de carga contienen el código ejecutable, los datos inicializados y otros elementos que el programa necesita en tiempo de ejecución.

En un ejecutable no PIE, las instrucciones de salto, los accesos a datos y las llamadas a funciones usan \emph{direcciones absolutas} fijas, lo que obliga al sistema operativo a cargarlo siempre en la misma dirección base. Un ejecutable \textbf{PIE} (\textit{Position Independent Executable}) usa exclusivamente \emph{referencias relativas} al \textit{instruction pointer} (\texttt{rip}), por lo que puede cargarse en cualquier dirección sin recompilación. Las direcciones que aparecen en el desensamblado son \textit{offsets} respecto al inicio del ELF, no direcciones reales en memoria.

\subsubsection*{Kernel}

El \textbf{kernel} (núcleo del sistema operativo) es el programa que se ejecuta con los mayores privilegios del procesador y actúa como intermediario entre los programas de usuario y el hardware. Administra la memoria, el procesador, los dispositivos y los sistemas de archivos.

\subsubsection*{/proc/\textless{}pid\textgreater{}/maps}

\texttt{/proc} es un \textbf{sistema de archivos virtual} del kernel de Linux: no existe en el disco; el kernel lo genera en tiempo real cuando algún programa lo lee. Dentro de \texttt{/proc}, cada proceso tiene un directorio \texttt{/proc/<pid>/} con archivos que exponen su estado interno. El archivo \texttt{/proc/<pid>/maps} describe la distribución del espacio de direcciones virtuales del proceso: cada línea corresponde a un segmento mapeado e indica su dirección de inicio, dirección de fin, permisos de acceso, offset en el archivo fuente y, si aplica, el nombre del archivo en disco.

\begin{lstlisting}[style=termstyle, caption={Ejemplo de linea en /proc/<pid>/maps para la Bomba}]
584ae0e57000-584ae0e5c000 r-xp 00000000 08:01 1234567  .../Bomba
\end{lstlisting}

La primera columna (\texttt{584ae0e57000}) es la dirección base donde el kernel cargó ese segmento.

\subsubsection*{ASLR — Address Space Layout Randomization}

El kernel implementa \textbf{ASLR}, que asigna una dirección base aleatoria a cada proceso en cada ejecución. Combinado con PIE, esto significa que la dirección de cualquier instrucción cambia en cada ejecución. Para colocar un breakpoint es necesario:
\begin{enumerate}[label=\arabic*.]
    \item Conocer el \textit{offset} de la instrucción en el ELF (obtenido del desensamblado).
    \item Determinar la dirección base real en runtime leyendo \texttt{/proc/<pid>/maps}.
    \item Calcular: $\texttt{dir\_real} = \texttt{base\_carga} + \texttt{offset\_ELF}$.
\end{enumerate}

\subsection{El uso de \texttt{ptrace}}

\texttt{ptrace} (\textit{process trace}) es una herramienta de Linux que permite a un proceso \textit{trazador} observar y controlar la ejecución de otro proceso \textit{trazado}.

La firma de \texttt{ptrace} es:

\begin{center}
\texttt{long ptrace(enum \_\_ptrace\_request \textbf{request}, pid\_t \textbf{pid}, void *\textbf{addr}, void *\textbf{data});}
\end{center}

\begin{description}
    \item[\texttt{request}] Operación a realizar (ver tabla a continuación).
    \item[\texttt{pid}] Identificador del proceso trazado.
    \item[\texttt{addr}] Dirección de memoria del trazado sobre la que operar. Se pasa \texttt{NULL} cuando la operación no requiere una dirección.
    \item[\texttt{data}] Dato adicional según la operación: señal a entregar, puntero a estructura de registros, valor a escribir, etc. Se pasa \texttt{NULL} cuando no aplica.
\end{description}

Las operaciones de \texttt{ptrace} utilizadas en este trabajo son:

\begin{center}
\begin{tabular}{lp{8.5cm}}
\toprule
\textbf{Operación} & \textbf{Descripción} \\
\midrule
\texttt{PTRACE\_TRACEME}  & El hijo se declara trazable por su padre. Los argumentos \texttt{pid}, \texttt{addr} y \texttt{data} son ignorados (se pasan 0, \texttt{NULL}, \texttt{NULL}). \\[4pt]
\texttt{PTRACE\_CONT}     & Reanuda la ejecución del trazado. \texttt{addr} es ignorado (\texttt{NULL}). \texttt{data} es la señal a entregar; \texttt{NULL} significa ninguna. \\[4pt]
\texttt{PTRACE\_PEEKTEXT} & Lee 8 bytes de la memoria del trazado en \texttt{addr}. \texttt{data} es ignorado (\texttt{NULL}). Devuelve el valor leído. \\[4pt]
\texttt{PTRACE\_POKETEXT} & Escribe el valor \texttt{data} en la memoria del trazado en \texttt{addr}. \\[4pt]
\texttt{PTRACE\_GETREGS}  & Copia todos los registros del trazado a la estructura apuntada por \texttt{data}. \texttt{addr} es ignorado (\texttt{NULL}). \\[4pt]
\texttt{PTRACE\_SETREGS}  & Escribe en los registros del trazado los valores de la estructura apuntada por \texttt{data}. \texttt{addr} es ignorado (\texttt{NULL}). \\
\bottomrule
\end{tabular}
\end{center}

\subsection{SIGTRAP y breakpoints de software}

\textbf{SIGTRAP} (\textit{Signal Trap} — señal de trampa) es una señal que el kernel envía a un proceso cuando ocurre un evento de depuración. Al recibir \texttt{SIGTRAP}, el proceso trazado se suspende automáticamente y el trazador es notificado a través de \texttt{waitpid}.

Un \textbf{breakpoint de software} consiste en reemplazar el primer byte de una instrucción con \texttt{0xCC}, que corresponde a la instrucción \texttt{INT3} (\textit{breakpoint interrupt}) del x86. Cuando el procesador ejecuta \texttt{INT3}, genera una interrupción que el kernel convierte en \texttt{SIGTRAP} para el proceso. Se eligió \texttt{0xCC} porque ocupa exactamente un byte, por lo que puede insertarse en cualquier instrucción sin desplazar el resto del código.

El procedimiento completo para usar un breakpoint con \texttt{ptrace} es:
\begin{enumerate}[label=\arabic*.]
    \item Leer los 8 bytes originales en la dirección objetivo con \texttt{PTRACE\_PEEKTEXT} y guardarlos.
    \item Escribir \texttt{0xCC} en el primer byte con \texttt{PTRACE\_POKETEXT}.
    \item Reanudar el trazado con \texttt{PTRACE\_CONT}.
    \item Cuando el breakpoint se dispara, \texttt{waitpid} retorna con señal \texttt{SIGTRAP}.
    \item Notar que \texttt{rip} apunta al byte \emph{siguiente} al \texttt{0xCC} (el CPU ya avanzó el \textit{instruction pointer}).
    \item Restaurar el byte original, corregir \texttt{rip} decrementándolo en 1 y continuar.
\end{enumerate}

\section{Implementación del desactivador}
% ================================================================

\subsection{Estrategia}

La estrategia consiste en colocar breakpoints en las instrucciones de comparación de cada fase. En ese preciso momento la Bomba ya calculó la clave esperada y la tiene disponible en un registro o en el stack. El desactivador lee ese valor e inyecta en la posición donde la Bomba espera la respuesta del usuario.

Para que la Bomba tenga algo que parsear con \texttt{sscanf}, se le envían seis respuestas ficticias a través de un pipe conectado a su \texttt{stdin}. El contenido de estas respuestas no importa ya que son sobreescritas por \texttt{ptrace} antes de la comparación.

\subsection{Arquitectura general}

El flujo general del desactivador es:
\begin{enumerate}[label=\arabic*.]
    \item Crear un pipe (canal) de comunicación entre padre e hijo.
    \item Llamar \texttt{fork()} pra crear un proceso hijo, idéntico al padre.
    \item El proceso hijo conecta su \texttt{stdin} al pipe para que su padre le inyecte las respuestas correctas.
    \item Se usa \texttt{execve} para remplazar el programa en ejecución por uno nuevo (el de la Bomba), con el fin de acceder a stack y segmentos de memoria.
    \item El padre espera el \texttt{SIGTRAP} inicial de \texttt{execve}, lee la dirección base del ELF y coloca 6 breakpoints.
    \item El padre escribe las respuestas ficticias en el pipe.
    \item El padre procesa los 6 breakpoints en orden: reanuda al hijo, espera el \texttt{SIGTRAP}, lee registros, inyecta la clave, restaura la instrucción y corrige \texttt{rip}.
    \item Reanuda al hijo hasta que termina.
\end{enumerate}

Las siguientes secciones describen cada función del programa. Las funciones del sistema utilizadas se describen junto a su primera aparición.

\subsection{Función \texttt{obtener\_direccion\_bomba}}

Recibe el PID del proceso hijo y devuelve la dirección base donde el sistema operativo cargó el ejecutable.

Para determinar esa dirección se lee el archivo virtual \texttt{/proc/<pid>/maps}, que el kernel mantiene por cada proceso en ejecución con la lista de todos sus segmentos de memoria: el ejecutable, las librerías dinámicas, el stack, el heap, etc. Se busca la línea que contiene el nombre \texttt{"Bomba"} y se extrae la dirección de inicio.

Funciones del sistema utilizadas:
\begin{description}
    \item[\texttt{snprintf(buffer, tamaño\_buffer, formato, ...)}] Escribe en el \texttt{buffer} una cadena formateada sin superar \texttt{tamaño\_buffer} bytes. Se usa para construir la ruta \texttt{/proc/<pid>/maps}.
    \item[\texttt{fopen(pathname, modo)}] Abre el archivo en \texttt{pathname} con el modo indicado (\texttt{"r"} = solo lectura). Devuelve un puntero a \texttt{FILE} o \texttt{NULL} si falló.
    \item[\texttt{fgets(buffer, tamaño\_buffer, archivo)}] Lee hasta \texttt{tamaño\_buffer-1} caracteres del archivo \texttt{archivo} y los guarda en \texttt{buffer} con terminador nulo. Devuelve \texttt{NULL} al fin de archivo o si ocurrió un error.
    \item[\texttt{strstr(cadena1, cadena2)}] Busca la primera ocurrencia de la cadena \texttt{cadena2} dentro de \texttt{cadena1}. Devuelve un puntero a la coincidencia o \texttt{NULL}.
    \item[\texttt{sscanf(buffer, formato, ...)}] Parsea el string en \texttt{buffer} según \texttt{formato} y guarda los resultados en las direcciones adicionales. Se usa con \texttt{\%lx} para extraer la dirección base en hexadecimal.
    \item[\texttt{fclose(archivo)}] Cierra el archivo representado por \texttt{archivo}.
\end{description}

\begin{lstlisting}[style=cstyle, caption={Funcion obtener\_direccion\_bomba}]
unsigned long obtener_direccion_bomba(pid_t id_proceso_bomba) {
    char path[64];
    snprintf(path, sizeof(path), "/proc/%d/maps", (int)id_proceso_bomba);
    FILE *procesos = fopen(path, "r");
    if (!procesos) {
        perror("Proceso no se Encuentra");
        exit(1);
    }
    unsigned long base = 0;
    char linea[512];
    while (fgets(linea, sizeof(linea), procesos)) {
        if (strstr(linea, "Bomba")) {
            sscanf(linea, "%lx-", &base);
            break;
        }
    }
    fclose(procesos);
    return base;
}
\end{lstlisting}

Se declara \texttt{base = 0}. El ciclo \texttt{while} lee el archivo línea por línea con \texttt{fgets}. Por cada línea, \texttt{strstr} verifica si contiene la cadena \texttt{"Bomba"}. Cuando la encuentra, \texttt{sscanf} extrae el número hexadecimal al inicio de la línea (la dirección base) y lo guarda en \texttt{base}. Si al terminar el ciclo \texttt{base} sigue en cero, el programa termina con error.

\subsection{Funciones \texttt{colocar\_breakpoint} y \texttt{quitar\_breakpoint}}

\texttt{colocar\_breakpoint} recibe el PID del hijo y la dirección donde colocar el breakpoint. Devuelve los 8 bytes originales de esa dirección para poder restaurarlos después.

\texttt{PTRACE\_PEEKTEXT} y \texttt{PTRACE\_POKETEXT} operan sobre palabras de 8 bytes alineados. Para no corromper los 7 bytes restantes de la instrucción, se aplica la máscara \texttt{\& \textasciitilde0xFFL} que preserva todos los bytes excepto el primero, y luego se realiza \texttt{| 0xCCL} para insertar el byte \texttt{0xCC}.

Dado que \texttt{PTRACE\_PEEKTEXT} puede devolver \texttt{-1} como valor legítimo de memoria, la única forma de detectar un error real es reseteando \texttt{errno} a cero antes de la llamada y verificando si cambió después.

\begin{lstlisting}[style=cstyle, caption={Funciones colocar\_breakpoint y quitar\_breakpoint}]
long colocar_breakpoint(pid_t id_proceso_bomba,
                        unsigned long direccion_breakpoint) {
    errno = 0;
    long bytes_originales = ptrace(PTRACE_PEEKTEXT,
                                   id_proceso_bomba,
                                   (void *)direccion_breakpoint,
                                   NULL);
    if (errno != 0) {
        perror("No se pudo copiar los bytes de 'direccion_breakpoint'");
        exit(1);
    }
    long interrupcion = (bytes_originales & ~0xFFL) | 0xCCL;
    if (ptrace(PTRACE_POKETEXT, id_proceso_bomba,
               (void *)direccion_breakpoint,
               (void *)interrupcion) < 0) {
        perror("No se pudo generar interrupcion");
        exit(1);
    }
    return bytes_originales;
}

void quitar_breakpoint(pid_t id_proceso_bomba,
                       unsigned long direccion_breakpoint_modificada,
                       long bytes_originales) {
    if (ptrace(PTRACE_POKETEXT, id_proceso_bomba,
               (void *)direccion_breakpoint_modificada,
               (void *)bytes_originales) < 0) {
        perror("No se pudieron restaurar los bytes originales");
        exit(1);
    }
}
\end{lstlisting}

\texttt{quitar\_breakpoint} recibe los mismos parámetros que \texttt{colocar\_breakpoint} más los bytes originales guardados, y simplemente los escribe de vuelta con \texttt{PTRACE\_POKETEXT}.

\subsection{Funciones \texttt{leer\_direccion\_memoria} e \texttt{inyectar}}

Las claves de tipo entero y float ocupan 4 bytes (32 bits). Sin embargo, \texttt{PTRACE\_PEEKTEXT} y \texttt{PTRACE\_POKETEXT} siempre operan con palabras de 8 bytes alineadas a 8. Las funciones \texttt{leer\_direccion\_memoria} e \texttt{inyectar} resuelven este desajuste.

\texttt{leer\_direccion\_memoria} recibe el PID y una dirección, y devuelve los 4 bytes almacenados en esa dirección. Primero calcula la dirección alineada (\texttt{addr \& \textasciitilde7UL}), lee los 8 bytes completos, calcula el desplazamiento en bits (\texttt{(addr \& 7) * 8}) y desplaza la palabra a la derecha para que los 4 bytes de interés queden en la parte baja, donde el cast a \texttt{uint32\_t} los extrae.

\texttt{inyectar} recibe el PID, una dirección y un valor de 32 bits a escribir. Lee primero los 8 bytes existentes para no perder los 4 bytes que no se quieren modificar. Luego aplica una máscara para limpiar los 4 bytes de destino y un OR con el valor desplazado para escribirlos.

\begin{lstlisting}[style=cstyle, caption={Funciones leer\_direccion\_memoria e inyectar}]
uint32_t leer_direccion_memoria(pid_t id_proceso_bomba,
                                unsigned long direccion_a_leer) {
    unsigned long alineado = direccion_a_leer & ~7UL;
    errno = 0;
    long leido = ptrace(PTRACE_PEEKTEXT, id_proceso_bomba,
                        (void *)alineado, NULL);
    if (errno != 0) {
        perror("No se pudo leer la memoria de interes");
        exit(1);
    }
    int desplazamiento = (int)((direccion_a_leer & 7) * 8);
    return (uint32_t)((uint64_t)leido >> desplazamiento);
}

void inyectar(pid_t id_proceso_bomba,
              unsigned long direccion_a_escribir,
              uint32_t contenido_a_escribir) {
    unsigned long alineado = direccion_a_escribir & ~7UL;
    errno = 0;
    uint64_t leido = (uint64_t)ptrace(PTRACE_PEEKTEXT, id_proceso_bomba,
                                      (void *)alineado, NULL);
    if (errno != 0) {
        perror("No se pudo leer memoria");
        exit(1);
    }
    int desplazamiento = (int)((direccion_a_escribir & 7) * 8);
    leido = (leido & ~(0xFFFFFFFFULL << desplazamiento))
          | ((uint64_t)contenido_a_escribir << desplazamiento);
    if (ptrace(PTRACE_POKETEXT, id_proceso_bomba,
               (void *)alineado, (void *)leido) < 0) {
        perror("No se pudo escribir memoria");
        exit(1);
    }
}
\end{lstlisting}

\textbf{Ejemplo}: para escribir en \texttt{[rsp+0x44]}, con \texttt{rsp} alineado a 8 bytes, la palabra de 8 bytes está en \texttt{rsp+0x40} y los 4 bytes a escribir comienzan en el byte 4. Por lo tanto \texttt{desplazamiento = 32}, y la máscara limpia exactamente esos 4 bytes antes de insertar el nuevo valor.

\subsection{Función principal}

La función \texttt{main} orquesta todo el proceso. Las funciones del sistema utilizadas en este bloque son:

\begin{description}
    \item[\texttt{pipe(pipefd)}] Crea un canal de comunicación unidireccional. Llena \texttt{pipefd[0]} con el descriptor de lectura y \texttt{pipefd[1]} con el de escritura. Un \texttt{fd} es un \textit{file descriptor}: variable que se utiliza en el código para referirse al número entero que identifica un canal de comunicación abierto por el sistema operativo.
    \item[\texttt{fork()}] No recibe parámetros. Crea un proceso hijo idéntico al padre. Devuelve 0 al hijo, el PID del hijo al padre, o -1 si falló.
    \item[\texttt{dup2(viejofd, nuevofd)}] Duplica el descriptor \texttt{viejofd} en \texttt{nuevofd}, cerrando \texttt{nuevofd} si ya estaba abierto. Se usa para conectar \texttt{stdin} del hijo al pipe.
    \item[\texttt{execve(pathname, argv, envp)}] Reemplaza el proceso actual por el programa ubicado en \texttt{pathname}: el kernel descarta el código y la memoria del proceso existente y carga en su lugar el nuevo ejecutable, comenzando su ejecución desde el punto de entrada. \texttt{argv} es un array de strings con los argumentos del nuevo programa, que debe terminar en \texttt{NULL}; el primer elemento es por convención el nombre del programa. \texttt{envp} es un array de strings con las variables de entorno, también terminado en \texttt{NULL}; se pasa \texttt{NULL} para heredar el entorno del proceso padre. Si \texttt{execve} tiene éxito, nunca retorna al código que lo llamó porque ese código ya no existe (el hijo nunca retorna, el padre sí lo ejecuta). En un proceso trazado con \texttt{PTRACE\_TRACEME}, el kernel genera automáticamente un \texttt{SIGTRAP} antes de ejecutar la primera instrucción del nuevo programa, dando al trazador la oportunidad de intervenir.
    \item[\texttt{waitpid(pid, status, options)}] Espera a que el proceso \texttt{pid} cambie de estado. El resultado se guarda en \texttt{status}. Con \texttt{options = 0}, el proceso padre queda suspendido hasta que el proceso hijo se detiene o termina.
    \item[\texttt{write(fd, buffer, n)}] Escribe \texttt{n} bytes del \texttt{buffer} al descriptor \texttt{fd}.
    \item[\texttt{close(fd)}] Cierra el descriptor \texttt{fd}.
    \item[\texttt{strlen(s)}] Devuelve la longitud de la cadena \texttt{s} sin el terminador nulo.
\end{description}

El bloque inicial de \texttt{main} crea el pipe y el proceso hijo. El orden es importante: el pipe se crea \emph{antes} del \texttt{fork} para que el hijo herede automáticamente ambos extremos.

\begin{lstlisting}[style=cstyle, caption={Creacion del pipe y del proceso hijo}]
int canal[2];
if (pipe(canal) < 0) {
    perror("No se pudo crear canal padre - hijo");
    return 1;
}
pid_t proceso_hijo = fork();
if (proceso_hijo < 0) {
    perror("No se pudo crear proceso hijo");
    return 1;
}
\end{lstlisting}

Dentro del bloque del hijo (\texttt{proceso\_hijo == 0}), se redirige \texttt{stdin} al extremo de lectura del pipe con \texttt{dup2}, se cierran los descriptores del pipe que ya no se necesitan, se declara el proceso trazable con \texttt{PTRACE\_TRACEME} y se reemplaza el proceso por la Bomba con \texttt{execve}.

\begin{lstlisting}[style=cstyle, caption={Bloque del proceso hijo}]
if (proceso_hijo == 0) {
    dup2(canal[0], STDIN_FILENO);
    close(canal[0]);
    close(canal[1]);
    ptrace(PTRACE_TRACEME, 0, NULL, NULL);
    char *av[] = { BOMB_PATH, NULL };
    execve(BOMB_PATH, av, NULL);
    perror("No se pudo remplazar el proceso por el de la bomba");
    _exit(1);
}
\end{lstlisting}

El padre cierra el extremo de lectura del pipe (solo escribe), espera el \texttt{SIGTRAP} inicial que genera \texttt{execve} en un proceso trazado, obtiene la dirección base y coloca los 6 breakpoints. Luego escribe las seis respuestas ficticias en el pipe, seguidas de un cierre del extremo de escritura.

\begin{lstlisting}[style=cstyle, caption={Inicializacion del padre}]
close(canal[0]);
int info_hijo;
waitpid(proceso_hijo, &info_hijo, 0);
if (!WIFSTOPPED(info_hijo)) {
    fprintf(stderr, "El hijo no se detuvo tras execve\n");
    return 1;
}
unsigned long base = obtener_direccion_bomba(proceso_hijo);
if (base == 0) {
    fprintf(stderr, "No se pudo determinar la direccion base\n");
    return 1;
}
unsigned long vector_direcciones_breakpoints[6] = {
    base + OFFSET_FASE1, base + OFFSET_FASE2, base + OFFSET_FASE3,
    base + OFFSET_FASE4, base + OFFSET_FASE5, base + OFFSET_FASE6,
};
long vector_contenido_previo[6];
for (int i = 0; i < 6; i++)
    vector_contenido_previo[i] = colocar_breakpoint(
                                     proceso_hijo,
                                     vector_direcciones_breakpoints[i]);
const char *respuestas = "0\n0.0\n0\nEstoSeSobreescribe\n0\n0.0\n";
write(canal[1], respuestas, strlen(respuestas));
close(canal[1]);
\end{lstlisting}

\subsection{Loop de procesamiento y manejo de señales}

El loop externo itera 6 veces, una por fase. Dentro, un loop interno reanuda al hijo con \texttt{PTRACE\_CONT} y espera su detención con \texttt{waitpid}. Si la señal recibida no es \texttt{SIGTRAP} (por ejemplo, una señal del linker dinámico), se la reenvía al hijo en el siguiente \texttt{PTRACE\_CONT} y se continúa esperando. Solo cuando se recibe \texttt{SIGTRAP} se sale del loop interno.

\begin{lstlisting}[style=cstyle, caption={Loop de procesamiento de breakpoints}]
struct user_regs_struct registros;
for (int fase = 0; fase < 6; fase++) {
    void *senial_hijo = NULL;
    for (;;) {
        if (ptrace(PTRACE_CONT, proceso_hijo, NULL, senial_hijo) < 0) {
            perror("No se pudo continuar"); return 1;
        }
        waitpid(proceso_hijo, &info_hijo, 0);
        if (WIFEXITED(info_hijo))   {
            fprintf(stderr, "El hijo terminó en fase %d\n", fase + 1);
            return 1;
        }
        if (!WIFSTOPPED(info_hijo)) {
            fprintf(stderr, "Estado inesperado en fase %d\n", fase + 1);
            return 1;
        }
        if (WSTOPSIG(info_hijo) == SIGTRAP) {
            break;
        }
        senial_hijo = (void *)(long)WSTOPSIG(info_hijo);
    }
    ptrace(PTRACE_GETREGS, proceso_hijo, NULL, &registros);
    unsigned long rip = registros.rip - 1;
    unsigned long rsp = registros.rsp;
    int indice = -1;
    for (int i = 0; i < 6; i++)
        if (rip == vector_direcciones_breakpoints[i])
            { indice = i; break; }
    if (indice < 0) { return 1; }
    /* ... inyeccion segun la fase (ver seccion siguiente) ... */
    quitar_breakpoint(proceso_hijo,
                      vector_direcciones_breakpoints[indice],
                      vector_contenido_previo[indice]);
    registros.rip = rip;
    ptrace(PTRACE_SETREGS, proceso_hijo, NULL, &registros);
}
ptrace(PTRACE_CONT, proceso_hijo, NULL, NULL);
waitpid(proceso_hijo, &info_hijo, 0);
\end{lstlisting}

Al detectar el \texttt{SIGTRAP}, \texttt{PTRACE\_GETREGS} copia todos los registros del hijo. Se resta 1 al valor de \texttt{rip} porque al ejecutar el \texttt{0xCC} el CPU avanzó el \textit{instruction pointer} un byte. Identificada la fase por comparación con las direcciones de los breakpoints, se inyecta la clave, se restaura la instrucción original y se corrige \texttt{rip} para que el hijo re-ejecute el \texttt{cmp} original con la clave ya inyectada. \texttt{PTRACE\_SETREGS} aplica todos los cambios al proceso hijo.

\subsection{Inyección por tipo de fase}

\begin{lstlisting}[style=cstyle, caption={Switch de inyeccion por fase}]
switch (indice) {
case 0:
    {
        uint32_t clave_correcta = (uint32_t)registros.r15;
        inyectar(proceso_hijo, rsp + 0x44, clave_correcta);
    }
    break;
case 1:
    {
        uint32_t clave_correcta = leer_direccion_memoria(
                                      proceso_hijo, rsp + 0x1c);
        inyectar(proceso_hijo, rsp + 0x48, clave_correcta);
    }
    break;
case 2:
    {
        uint32_t clave_correcta = (uint32_t)registros.rbx;
        inyectar(proceso_hijo, rsp + 0x44, clave_correcta);
    }
    break;
case 3:
    registros.rdi = registros.rsi;
    break;
case 4:
    {
        uint32_t clave_correcta = (uint32_t)registros.rbx;
        inyectar(proceso_hijo, rsp + 0x44, clave_correcta);
    }
    break;
case 5:
    {
        uint32_t clave_correcta = leer_direccion_memoria(proceso_hijo, rsp + 0x3c);
        inyectar(proceso_hijo, rsp + 0x4c, clave_correcta);
    }
    break;
}
\end{lstlisting}

Las llaves dentro de cada \texttt{case} son necesarias para declarar variables locales sin que sean visibles en los casos siguientes.

La Fase~4 merece una explicación especial. En lugar de copiar el string esperado al buffer del usuario, se modifica el registro \texttt{rdi} (primer argumento de \texttt{strcmp}) para que apunte a la misma dirección que \texttt{rsi} (el string esperado en \texttt{[rsp+0x50]}). Así, \texttt{strcmp} compara el string esperado consigo mismo, retorna siempre 0 y la fase pasa sin necesidad de conocer ni copiar el string.

\section{Conclusión}
% ================================================================

Se implementó exitosamente un programa en C que desactiva las seis fases de la bomba utilizando la llamada al sistema \texttt{ptrace}.

La estrategia de inyección en el punto de comparación resultó ser elegante y robusta: al actuar sobre los operandos en el preciso momento en que se evalúan, el desactivador no necesita conocer la aritmética interna del binario ni la semilla aleatoria. El proceso de ingeniería inversa se centró únicamente en identificar \textit{dónde} está cada comparación y \textit{qué registro o posición de memoria} contiene el valor correcto, dejando toda la complejidad aritmética al propio binario.

El trabajo permitió poner en práctica conceptos fundamentales de arquitectura de computadoras y sistemas operativos: el formato ELF y el mecanismo PIE/ASLR, el funcionamiento de \texttt{ptrace}, la implementación de breakpoints de software con la instrucción \texttt{INT3}, y la manipulación directa de registros y memoria de un proceso en ejecución.
