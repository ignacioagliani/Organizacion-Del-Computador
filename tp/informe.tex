\section{Introducción}
% ================================================================

El \textit{BombLab} es un ejercicio clásico de ingeniería inversa propuesto originalmente por Bryant y O'Hallaron en la Universidad Carnegie Mellon. En su versión tradicional, un ejecutable solicita seis claves al usuario; si alguna es incorrecta, la ``bomba explota'' y el proceso termina con error. Como las claves están codificadas en el binario, es posible encontrarlas mediante análisis estático del código ensamblador.

La variante presentada en este trabajo introduce una diferencia fundamental: \textbf{las claves no están almacenadas en el ejecutable sino que se generan aleatoriamente en cada ejecución}, utilizando la función \texttt{rand()} inicializada con \texttt{srand(time(NULL))}. Esto hace que el análisis estático sea insuficiente: no existe ninguna clave fija que pueda extraerse del binario con antelación.

El objetivo del trabajo es escribir un programa en C que:
\begin{enumerate}[label=\arabic*.]
    \item Ejecute el binario \texttt{Bomba} como proceso hijo.
    \item Utilice la llamada al sistema \texttt{ptrace} para interceptar su ejecución en tiempo real.
    \item Lea el valor esperado en cada fase directamente desde los registros o la memoria del proceso.
    \item Inyecte ese valor en el operando que representa la respuesta del usuario, justo antes de que se evalúe la comparación.
    \item Logre pasar las seis fases sin que la bomba detone.
\end{enumerate}

Este informe detalla los conceptos teóricos involucrados, el análisis del ejecutable mediante ingeniería inversa y el diseño del programa \texttt{desactivador.c}.

\section{Conceptos fundamentales}
% ================================================================

\subsection{Formato ELF y ejecutables PIE}

Los programas en Linux se almacenan en formato \textbf{ELF} (\textit{Executable and Linkable Format}). Un archivo ELF contiene, entre otras cosas, \textit{segmentos de carga} que el sistema operativo mapea en memoria virtual cuando ejecuta el programa. Cada segmento tiene una dirección virtual de carga definida en el encabezado del ELF.

Un ejecutable \textbf{PIE} (\textit{Position Independent Executable}) puede ser cargado en cualquier dirección de memoria, ya que todas sus instrucciones usan referencias relativas al \textit{instruction pointer} (\texttt{rip}) en lugar de direcciones absolutas. Las direcciones que aparecen en el desensamblado son \textit{offsets} relativos a la base, no direcciones reales en memoria.

El binario \texttt{Bomba} es un ELF64 PIE. Una de sus instrucciones en el desensamblado aparece en \texttt{0x176e}, pero en tiempo de ejecución estará en alguna dirección como \texttt{0x584ae0e5876e}, dependiendo de dónde el sistema operativo lo haya cargado.

\subsubsection*{ASLR — Address Space Layout Randomization}

El kernel de Linux implementa \textbf{ASLR}, que asigna una dirección base aleatoria a cada proceso en cada ejecución. Combinado con PIE, esto significa que la dirección de cualquier instrucción cambia en cada ejecución. Por lo tanto, para colocar un breakpoint es necesario:
\begin{enumerate}[label=\arabic*.]
    \item Conocer el \textit{offset} de la instrucción en el ELF (obtenido del desensamblado).
    \item Determinar la dirección base real en runtime.
    \item Calcular: $\texttt{dir\_real} = \texttt{base\_carga} + \texttt{offset\_ELF}$.
\end{enumerate}

La dirección base se obtiene leyendo el archivo \texttt{/proc/<pid>/maps}, que lista todos los segmentos mapeados del proceso.

\subsection{La llamada al sistema \texttt{ptrace}}

\texttt{ptrace} (\textit{process trace}) es una llamada al sistema de Linux que permite a un proceso \textit{trazador} (\textit{tracer}) observar y controlar la ejecución de otro proceso \textit{trazado} (\textit{tracee}). Es la base sobre la que se construyen los depuradores como GDB y LLDB.

El mecanismo general es el siguiente: cuando el tracee recibe una señal (incluido \texttt{SIGTRAP}, generado por los breakpoints), se suspende y el tracer es notificado vía \texttt{waitpid()}. El tracer puede entonces leer y modificar el estado completo del tracee (registros y memoria) antes de reanudarlo.

Las operaciones de \texttt{ptrace} utilizadas en este trabajo son:

\begin{center}
\begin{tabular}{lp{9cm}}
\toprule
\textbf{Operación} & \textbf{Descripción} \\
\midrule
\texttt{PTRACE\_TRACEME}  & El proceso hijo se declara trazable por su padre. Debe llamarse antes de \texttt{execve}. \\[4pt]
\texttt{PTRACE\_CONT}     & Reanuda la ejecución del tracee. Opcionalmente entrega una señal al proceso. \\[4pt]
\texttt{PTRACE\_PEEKTEXT} & Lee una palabra de 8 bytes de la memoria virtual del tracee. \\[4pt]
\texttt{PTRACE\_POKETEXT} & Escribe una palabra de 8 bytes en la memoria virtual del tracee. \\[4pt]
\texttt{PTRACE\_GETREGS}  & Copia todos los registros del procesador (rip, rsp, rax, rbx, \ldots, r15) a una estructura \texttt{user\_regs\_struct} en el tracer. \\[4pt]
\texttt{PTRACE\_SETREGS}  & Escribe valores en los registros del tracee a partir de una estructura \texttt{user\_regs\_struct}. \\
\bottomrule
\end{tabular}
\end{center}

\subsection{Breakpoints de software}

Un \textbf{breakpoint de software} consiste en reemplazar el primer byte de una instrucción con \texttt{0xCC}, que corresponde a la instrucción \texttt{INT3} (\textit{breakpoint interrupt}) del x86. Cuando el procesador ejecuta \texttt{INT3}, genera automáticamente una excepción que el sistema operativo convierte en una señal \texttt{SIGTRAP} para el proceso.

El procedimiento completo para colocar y usar un breakpoint es:

\begin{enumerate}[label=\arabic*.]
    \item \textbf{Leer} el byte original en la dirección objetivo (con \texttt{PTRACE\_PEEKTEXT}).
    \item \textbf{Guardarlo} para poder restaurarlo después.
    \item \textbf{Escribir} \texttt{0xCC} en esa dirección (con \texttt{PTRACE\_POKETEXT}).
    \item \textbf{Reanudar} el tracee con \texttt{PTRACE\_CONT}.
    \item Cuando el breakpoint se dispara, \texttt{waitpid} retorna con señal \texttt{SIGTRAP}.
    \item \textbf{Notar} que \texttt{rip} apunta al byte \emph{siguiente} al \texttt{0xCC} (el CPU ya incrementó el PC al ejecutar \texttt{INT3}).
    \item \textbf{Restaurar} el byte original con \texttt{PTRACE\_POKETEXT}.
    \item \textbf{Corregir} \texttt{rip} decrementándolo en 1 con \texttt{PTRACE\_SETREGS}, para que apunte de nuevo a la instrucción original.
    \item \textbf{Realizar} las modificaciones deseadas (registros, memoria).
    \item \textbf{Continuar} con \texttt{PTRACE\_CONT}.
\end{enumerate}

\section{Análisis del ejecutable}
% ================================================================

\subsection{Información general}

\begin{lstlisting}[style=termstyle]
$ file Bomba
Bomba: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV),
       dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
       BuildID[sha1]=2ec7e50a..., for GNU/Linux 3.2.0, stripped
\end{lstlisting}

Características relevantes del binario:
\begin{itemize}
    \item \textbf{Arquitectura}: x86-64 (64 bits, little-endian).
    \item \textbf{Tipo}: ELF PIE, enlazado dinámicamente.
    \item \textbf{Símbolos}: \textit{stripped} — no contiene información de debug ni nombres de funciones.
    \item \textbf{Librerías}: \texttt{libc} estándar. Las funciones importadas visibles en el PLT son: \texttt{rand}, \texttt{srand}, \texttt{time}, \texttt{fgets}, \texttt{sscanf}, \texttt{strcmp}, \texttt{strcspn}, \texttt{puts}, \texttt{printf}, \texttt{exit}.
\end{itemize}

El análisis se realizó con \texttt{objdump -d Bomba}, cuyo resultado completo se encuentra en \texttt{desensamblado.txt}.

\subsection{Flujo de ejecución}

Al iniciarse, la función \texttt{main} del binario sigue este patrón:

\begin{enumerate}[label=\arabic*.]
    \item Llama a \texttt{time(NULL)} para obtener la marca de tiempo actual en segundos.
    \item Usa ese valor como semilla con \texttt{srand()}.
    \item Realiza 28 llamadas a \texttt{rand()} y aplica operaciones aritméticas (XOR, sumas, módulos) para derivar las claves de las seis fases. Todas quedan almacenadas en registros o en el stack antes de mostrar el primer prompt.
    \item Para cada fase, en orden: imprime un prompt, lee la respuesta del usuario con \texttt{fgets} + \texttt{sscanf} (o solo \texttt{fgets} + \texttt{strcmp} para la fase de texto), compara con la clave esperada y, si no coincide, salta a la función de detonación que imprime \texttt{BOOM!} y termina con \texttt{exit(1)}.
\end{enumerate}

\subsection{Las seis fases}

El análisis del desensamblado permitió identificar las instrucciones de comparación de cada fase, los offsets desde la base PIE y qué registro o posición de memoria contiene el valor esperado:

\begin{center}
\begin{tabular}{cclll}
\toprule
\textbf{Fase} & \textbf{Tipo} & \textbf{Offset ELF} & \textbf{Instrucción de comparación} & \textbf{Clave esperada en} \\
\midrule
1 & Entero & \texttt{0x176e} & \texttt{cmp [rsp+0x44], r15d}         & registro \texttt{r15d} \\
2 & Float  & \texttt{0x17c8} & \texttt{ucomiss xmm3, [rsp+0x48]}    & memoria \texttt{[rsp+0x1c]} \\
3 & Entero & \texttt{0x182f} & \texttt{cmp [rsp+0x44], ebx}          & registro \texttt{ebx} \\
4 & Texto  & \texttt{0x18ae} & \texttt{call strcmp(rdi, rsi)}         & \texttt{rsi} $\to$ string esperado \\
5 & Entero & \texttt{0x1911} & \texttt{cmp [rsp+0x44], ebx}          & registro \texttt{ebx} \\
6 & Float  & \texttt{0x195f} & \texttt{ucomiss xmm4, [rsp+0x4c]}    & memoria \texttt{[rsp+0x3c]} \\
\bottomrule
\end{tabular}
\end{center}

En todos los casos, la respuesta del usuario es leída por \texttt{sscanf} (formatos \texttt{\%d} para enteros y \texttt{\%f} para floats) y almacenada en \texttt{[rsp+0x44]} (enteros) o \texttt{[rsp+0x48]}/\texttt{[rsp+0x4c]} (floats). La bomba compara ese valor con la clave esperada.

\subsection{Detalle de las comparaciones}

\subsubsection*{Fases 1, 3 y 5 — Enteros}

La estructura es idéntica en los tres casos: el usuario debe ingresar el valor exacto que está almacenado en un registro. En la fase 1 ese registro es \texttt{r15d}; en las fases 3 y 5 es \texttt{ebx}, aunque con distinto valor en cada caso ya que se calcula en distintos momentos de la ejecución.

\begin{lstlisting}[style=asmstyle, caption={Comparación de entero — Fase 1 (offset \texttt{0x176e})}]
176e:  44 39 7c 24 44   cmp  DWORD PTR [rsp+0x44], r15d
1773:  0f 85 22 02 00   jne  199b    ; saltar a BOOM! si no coincide
\end{lstlisting}

\subsubsection*{Fases 2 y 6 — Punto flotante}

Los floats se comparan con la instrucción SSE \texttt{ucomiss}, que compara dos valores en precisión simple (\texttt{float} de 32 bits). El valor esperado se carga en un registro XMM desde el stack y se compara con el input del usuario.

\begin{lstlisting}[style=asmstyle, caption={Comparación de float — Fase 2 (offset \texttt{0x17c2})}]
17c2:  f3 0f 10 5c 24 1c   movss   xmm3, DWORD PTR [rsp+0x1c]  ; carga clave
17c8:  0f 2e 5c 24 48      ucomiss xmm3, DWORD PTR [rsp+0x48]  ; compara con input
17cd:  0f 8a c8 01 00 00   jp      199b    ; BOOM si NaN (parity flag)
17d3:  0f 85 c2 01 00 00   jne     199b    ; BOOM si no son iguales
\end{lstlisting}

La instrucción \texttt{ucomiss} activa el \textit{parity flag} si alguno de los operandos es NaN. Las dos ramas condicionales (\texttt{jp} y \texttt{jne}) garantizan que tanto NaN como valores distintos detonen la bomba.

\subsubsection*{Fase 4 — Texto}

La bomba construye un string de 15 caracteres ASCII imprimibles (generados con \texttt{rand() \% 93 + 33}) y lo almacena en \texttt{[rsp+0x50]}. El usuario debe ingresar exactamente ese string. La comparación se hace con \texttt{strcmp}.

\begin{lstlisting}[style=asmstyle, caption={Comparación de string — Fase 4 (offset \texttt{0x18ae})}]
18a1:  48 8d 74 24 50   lea  rsi, [rsp+0x50]        ; rsi = string esperado
18a6:  48 89 ef         mov  rdi, rbp               ; rdi = buffer del usuario
18a9:  c6 44 04 60 00   mov  BYTE PTR [rsp+rax+0x60], 0x0  ; null-terminar input
18ae:  e8 8d f8 ff ff   call strcmp                  ; compara
18b3:  85 c0            test eax, eax
18b5:  0f 85 e0 00 00   jne  199b                   ; BOOM si != 0
\end{lstlisting}

El string esperado ocupa 15 bytes más un terminador nulo en \texttt{[rsp+0x5f]}.

\section{Implementación del desactivador}
% ================================================================

\subsection{Estrategia de inyección}

Existen dos enfoques posibles para resolver el problema:

\begin{description}
    \item[Enfoque A — Replicar la aritmética:] Capturar la semilla de \texttt{srand} con ptrace y reproducir en el proceso padre todas las operaciones del binario (28 llamadas a \texttt{rand()} seguidas de operaciones de XOR, suma y módulo) para calcular las 6 claves de antemano. Se escriben las respuestas correctas en el pipe antes de que el hijo las pida.

    \textit{Ventaja:} una sola lectura, sin necesidad de múltiples breakpoints. \textit{Desventaja:} requiere reimplementar exactamente la aritmética de división entera con ``números mágicos'' que usa el compilador, y las conversiones de punto flotante. Cualquier error de precisión hace fallar la fase correspondiente.

    \item[Enfoque B — Inyección en el punto de comparación:] Colocar breakpoints en las instrucciones de comparación. En ese momento la clave esperada ya está calculada y disponible en registros o en el stack. Se sobreescribe el operando que representa la respuesta del usuario con el valor correcto.

    \textit{Ventaja:} no depende de ningún detalle aritmético del binario ni de la semilla. \textit{Desventaja:} requiere 6 breakpoints y enviar respuestas ficticias en el pipe.
\end{description}

Se optó por el \textbf{Enfoque B} por ser más robusto y menos propenso a errores. Las respuestas ficticias enviadas al pipe (\texttt{"0"}, \texttt{"0.0"}, etc.) son leídas por \texttt{fgets} pero sus valores son irrelevantes: ptrace los sobreescribe antes de que se ejecute la comparación.

\subsection{Arquitectura del programa}

El flujo general de \texttt{desactivador.c} es el siguiente:

\begin{enumerate}[label=\arabic*.]
    \item Crear un pipe (extremo de escritura para el padre, extremo de lectura como stdin del hijo).
    \item Hacer \texttt{fork()}. El hijo: conecta stdin al pipe, llama a \texttt{PTRACE\_TRACEME} y ejecuta \texttt{execve("./Bomba")}.
    \item El padre espera el \texttt{SIGTRAP} inicial que \texttt{execve} genera en un proceso trazado.
    \item El padre lee \texttt{/proc/<pid>/maps} para obtener la dirección base del ELF.
    \item El padre coloca 6 breakpoints y escribe 6 respuestas ficticias en el pipe.
    \item El padre entra en un loop que procesa cada breakpoint en orden:
    \begin{enumerate}[label=\alph*)]
        \item Reanuda al hijo con \texttt{PTRACE\_CONT}.
        \item Espera \texttt{SIGTRAP} (otras señales se reenvían al hijo).
        \item Lee registros con \texttt{PTRACE\_GETREGS}.
        \item Inyecta el valor correcto según el tipo de fase.
        \item Restaura la instrucción original y corrige \texttt{rip}.
        \item Aplica los cambios con \texttt{PTRACE\_SETREGS}.
    \end{enumerate}
    \item Tras los 6 breakpoints, reanuda al hijo hasta que termina.
\end{enumerate}

\subsection{Detección de la dirección base}

\begin{lstlisting}[style=cstyle, caption={Función \texttt{get\_base}: dirección base del ELF PIE desde \texttt{/proc/pid/maps}}]
static unsigned long get_base(pid_t pid)
{
    char path[64];
    snprintf(path, sizeof(path), "/proc/%d/maps", (int)pid);
    FILE *f = fopen(path, "r");

    unsigned long base = 0;
    char line[512];
    while (fgets(line, sizeof(line), f)) {
        if (strstr(line, "Bomba")) {      /* buscar la entrada del binario */
            sscanf(line, "%lx-", &base);
            break;
        }
    }
    fclose(f);
    return base;
}
\end{lstlisting}

La primera entrada en \texttt{/proc/<pid>/maps} que corresponde al binario \texttt{Bomba} indica la dirección donde fue cargado su primer segmento (el que corresponde a la dirección virtual 0x0 en el ELF). Sumando un offset del desensamblado a esta base se obtiene la dirección real de cualquier instrucción en el proceso.

\subsection{Gestión de breakpoints}

\begin{lstlisting}[style=cstyle, caption={Colocación y remoción de breakpoints de software}]
static long set_bp(pid_t pid, unsigned long addr)
{
    long orig = ptrace(PTRACE_PEEKTEXT, pid, (void *)addr, NULL);
    /* Reemplazar solo el primer byte con 0xCC, preservar los 7 restantes */
    long patched = (orig & ~0xFFL) | 0xCCL;
    ptrace(PTRACE_POKETEXT, pid, (void *)addr, (void *)patched);
    return orig;   /* devolver para restaurar luego */
}

static void rm_bp(pid_t pid, unsigned long addr, long orig)
{
    ptrace(PTRACE_POKETEXT, pid, (void *)addr, (void *)orig);
}
\end{lstlisting}

\texttt{PTRACE\_POKETEXT} opera sobre palabras de 8 bytes. Para no corromper los 7 bytes restantes de la instrucción, se aplica una máscara \texttt{\&}\;\texttt{\textasciitilde{}0xFFL} que preserva todos los bytes excepto el primero, y luego se OR con \texttt{0xCCL} para insertar el breakpoint.

\subsection{Lectura y escritura de 32 bits en la memoria del tracee}

Las claves de tipo entero y float ocupan 4 bytes (32 bits). Sin embargo, \texttt{PTRACE\_PEEKTEXT/POKETEXT} siempre opera con palabras de 8 bytes alineadas. Las funciones \texttt{peek32} y \texttt{poke32} resuelven este desajuste:

\begin{lstlisting}[style=cstyle, caption={Funciones de acceso a 32 bits en memoria del tracee}]
static uint32_t peek32(pid_t pid, unsigned long addr)
{
    unsigned long aligned = addr & ~7UL;   /* alinear a 8 bytes */
    long w = ptrace(PTRACE_PEEKTEXT, pid, (void *)aligned, NULL);
    int shift = (int)((addr & 7) * 8);    /* offset en bits dentro de la palabra */
    return (uint32_t)((uint64_t)w >> shift);
}

static void poke32(pid_t pid, unsigned long addr, uint32_t val)
{
    unsigned long aligned = addr & ~7UL;
    uint64_t w = (uint64_t)ptrace(PTRACE_PEEKTEXT, pid, (void *)aligned, NULL);
    int shift = (int)((addr & 7) * 8);
    /* Limpiar los 4 bytes de destino y escribir el nuevo valor */
    w = (w & ~(0xFFFFFFFFULL << shift)) | ((uint64_t)val << shift);
    ptrace(PTRACE_POKETEXT, pid, (void *)aligned, (void *)w);
}
\end{lstlisting}

\textbf{Ejemplo}: para acceder a \texttt{[rsp+0x1c]}, con \texttt{rsp} alineado a 8 bytes: la palabra de 8 bytes está en \texttt{rsp+0x18} y los 4 bytes del float comienzan en el byte 4 de esa palabra. Por lo tanto \texttt{shift = 32}, y la operación de desplazamiento extrae exactamente los 4 bytes deseados.

\subsection{El loop principal y manejo de señales}

\begin{lstlisting}[style=cstyle, caption={Loop de procesamiento de breakpoints con manejo de señales inesperadas}]
for (int phase = 0; phase < 6; phase++) {
    void *sig_to_deliver = NULL;
    for (;;) {
        ptrace(PTRACE_CONT, child, NULL, sig_to_deliver);
        waitpid(child, &status, 0);
        if (WIFEXITED(status)) { /* salida prematura */ return 1; }
        if (WSTOPSIG(status) == SIGTRAP) break;   /* nuestro breakpoint */
        /* Otra senal (ej. del linker): reenviarla y seguir esperando */
        sig_to_deliver = (void *)(long)WSTOPSIG(status);
    }
    ptrace(PTRACE_GETREGS, child, NULL, &regs);
    unsigned long rip = regs.rip - 1;   /* posicion real del 0xCC */
    unsigned long rsp = regs.rsp;
    /* ... identificar breakpoint, inyectar valor, restaurar ... */
    rm_bp(child, bp_addr[idx], bp_orig[idx]);
    regs.rip = rip;                      /* corregir rip */
    ptrace(PTRACE_SETREGS, child, NULL, &regs);
}
\end{lstlisting}

El loop interno garantiza que señales ajenas al programa (como las que puede enviar el linker dinámico durante la carga) no interrumpan el flujo: se reenvían al hijo con \texttt{PTRACE\_CONT} y se continúa esperando el \texttt{SIGTRAP} propio.

\subsection{Inyección por tipo de fase}

\begin{lstlisting}[style=cstyle, caption={Lógica de inyección para cada una de las seis fases}]
switch (idx) {
case 0: /* Fase 1 -- entero: clave en r15d, input usuario en [rsp+0x44] */
    poke32(child, rsp + 0x44, (uint32_t)regs.r15);
    break;

case 1: /* Fase 2 -- float: clave en [rsp+0x1c], input usuario en [rsp+0x48] */
    poke32(child, rsp + 0x48, peek32(child, rsp + 0x1c));
    break;

case 2: /* Fase 3 -- entero: clave en ebx, input usuario en [rsp+0x44] */
    poke32(child, rsp + 0x44, (uint32_t)regs.rbx);
    break;

case 3: /* Fase 4 -- texto: rdi = rsi -> strcmp compara el string consigo mismo */
    regs.rdi = regs.rsi;
    break;

case 4: /* Fase 5 -- entero: clave en ebx, input usuario en [rsp+0x44] */
    poke32(child, rsp + 0x44, (uint32_t)regs.rbx);
    break;

case 5: /* Fase 6 -- float: clave en [rsp+0x3c], input usuario en [rsp+0x4c] */
    poke32(child, rsp + 0x4c, peek32(child, rsp + 0x3c));
    break;
}
\end{lstlisting}

La fase 4 merece una explicación especial. En lugar de copiar el string esperado al buffer del usuario, se modifica el registro \texttt{rdi} (primer argumento de \texttt{strcmp}) para que apunte a la misma dirección que \texttt{rsi} (segundo argumento, el string esperado). Así, \texttt{strcmp} compara el string esperado \textit{consigo mismo}, retorna siempre 0, y la fase pasa sin necesidad de conocer ni copiar el contenido del string.

\section{Conclusión}
% ================================================================

Se implementó exitosamente un programa en C que desactiva las seis fases de la bomba utilizando la llamada al sistema \texttt{ptrace}.

La estrategia de inyección en el punto de comparación resultó ser elegante y robusta: al actuar sobre los operandos en el preciso momento en que se evalúan, el desactivador no necesita conocer la aritmética interna del binario ni la semilla aleatoria de cada ejecución. El proceso de ingeniería inversa se centró únicamente en identificar \textit{dónde} está cada comparación y \textit{qué registro o posición de memoria} contiene el valor correcto, dejando toda la complejidad aritmética al propio binario.

El trabajo permitió poner en práctica de forma concreta conceptos fundamentales de arquitectura de computadoras y sistemas operativos: el formato ELF y el mecanismo PIE/ASLR, el funcionamiento a bajo nivel de \texttt{ptrace}, la implementación de breakpoints de software con la instrucción \texttt{INT3}, y la manipulación directa de registros y memoria de un proceso en ejecución.
